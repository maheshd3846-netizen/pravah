# PRAVAH — Phase 3B: Counterfactual Plan Evaluation & Closed-Loop Validation

## 1. Purpose

In forward military supply chain logistics, mathematical optimization alone is insufficient: an optimizer may discover an "optimal" solution under mathematical assumptions (linearized delays, static capacity bounds, deterministic demand approximations) that fails or behaves unexpectedly when executed inside a non-linear, stochastic physical environment subject to blizzards, road degradations, and inventory balance dynamics.

**The fundamental question answered by Phase 3B is:**
> *Does the logistics plan generated by the optimizer actually improve operational outcomes when injected into the same disrupted environment under strictly controlled conditions?*

PRAVAH implements a closed-loop validation engine where decisions are converted into executable physical convoys, simulated against an identical non-intervened baseline, and quantitatively audited across multiple operational dimensions.

---

## 2. Experimental Design: Paired Counterfactual Architecture

To isolate the causal effect of the optimizer's decisions from environmental randomness, the evaluation relies on **paired counterfactual simulation**:

```
                     OptimizationPlan (Phase 3A)
                                ↓
                      OptimizationPlanAdapter
                     (Pre-simulation Validation)
                                ↓
                       StateSnapshot.capture()
                       [SHA-256 State Hash]
                                ↓
                ┌───────────────┴───────────────┐
                ↓                               ↓
       BASELINE SIMULATION            INTERVENTION SIMULATION
        (Identical Seed,                (Identical Seed,
         Identical State,                Identical State,
         Identical Weather,              Identical Weather,
         Identical Disruptions,          Identical Disruptions,
         No Intervention)                Optimizer Injected Shipments)
                ↓                               ↓
        Baseline Metrics                Optimized Metrics
                └───────────────┬───────────────┘
                                ↓
                         Metric Deltas
                                ↓
                        Tradeoff Analysis
                                ↓
               VERDICT: IMPROVED / MIXED / DEGRADED
```

Both runs originate from the exact same bitwise state snapshot and experience identical demand realizations, weather trajectories, and route disruptions over the identical horizon ($24\text{h}$, $72\text{h}$, or $168\text{h}$).

## 3. State Snapshot Architecture (`simulation/state_snapshot.py`)

The `StateSnapshot` class provides bitwise-reproducible state capture, deterministic serialization, and isolated restoration without mutable object aliasing.

### Core Interface
- `capture(simulator: Simulator) -> StateSnapshot`: Serializes world nodes, initial inventories, dynamic route statuses, vehicle states, in-transit shipments, and active disruptions.
- `clone() -> StateSnapshot`: Generates a deep, detached copy of the snapshot.
- `restore_into(simulator: Simulator) -> None`: Replaces the simulator's mutable state directly with snapshot data.
- `hash() -> str`: Computes a deterministic SHA-256 fingerprint over normalized, sorted JSON state keys.

### State Hash Guard
Before simulating the counterfactual intervention, the evaluator verifies:
$$\text{hash}(\text{snapshot}_{\text{baseline}}) == \text{hash}(\text{snapshot}_{\text{intervention}})$$
If a hash divergence is detected, evaluation is terminated immediately with status `INVALID` to prevent invalid causal claims.

---

## 4. Baseline Definition

The **Baseline Simulation** represents the counterfactual status quo:
- The exact operational scenario (e.g., `COMPOUND_DISRUPTION`) runs with zero optimizer dispatches.
- Existing standard baseline replenish mechanics and forward consumptions run naturally.
- The baseline is never artificially crippled; it represents what would occur if commanders took no intervention.

---

## 5. Intervention Definition & Commodity Mapping (`optimization/plan_adapter.py`)

The **Intervention Simulation** starts from the same initial state. The optimizer's recommended movements are validated and converted into physical discrete shipments:
- Each decision is mapped to source node, destination node, commodity, quantity, route, vehicle, and dispatch hour.
- **Physical Movement Realism**: Shipments are NOT instantaneously teleported. The source node's inventory is deducted at dispatch, the assigned vehicle transitions to `IN_TRANSIT`, transit time is computed dynamically based on simulated route terrain and weather, and destination inventory is credited only upon physical arrival at `actual_arrival`.
- **Cross-Layer Commodity Mapping**: Phase 3A optimization terminology (`RATIONS`, `AMMUNITION`) is bridged cleanly into Phase 1 discrete categories (`FOOD`, `GENERAL_CRITICAL`) through `OPTIMIZER_TO_SIM_COMMODITY` without modifying either layer's core abstractions.

---

## 6. Random Seed & Reproducibility Strategy

- Deterministic world generation, weather transitions, and stochastic demand variations are anchored by explicit `seed` parameters passed into `SimulationConfig`.
- Common random numbers (CRN) ensure that both runs encounter identical shocks at identical hours.
- Automated tests (`test_deterministic_evaluation`) verify that evaluating the same plan twice yields bitwise identical initial hashes, identical baseline metrics, and identical verdicts.

## 7. Operational Evaluation Metrics (`SimulationRunMetrics`)

The evaluator tracks comprehensive operational KPIs rather than single-metric proxies:

| Category | Metric | Definition |
| :--- | :--- | :--- |
| **Inventory** | `initial_inventory_total` | Total starting stock across all nodes and commodities |
| | `final_inventory_total` | Total ending stock at conclusion of simulation horizon |
| | `minimum_inventory_total` | Lowest aggregate inventory level recorded |
| | `average_inventory_total` | Mean aggregate inventory across all simulation hours |
| **Service** | `total_requested_demand` | Cumulative demand requested by all forward units |
| | `total_fulfilled_demand` | Demand successfully satisfied from local stock |
| | `total_unmet_demand` | Cumulative demand that could not be satisfied |
| | `fulfillment_rate_percent` | $\frac{\text{fulfilled}}{\text{requested}} \times 100\%$ |
| **Stockout** | `total_stockout_events` | Total stockout occurrences ($I_{n,k,t} = 0$ with active demand) |
| | `stockout_duration_hours` | Cumulative duration of stockout states |
| | `nodes_affected_stockout` | Distinct nodes experiencing stockout |
| | `items_affected_stockout` | Distinct commodities depleted |
| **Safety Stock** | `safety_stock_breaches` | Incidents where inventory dipped below safety thresholds |
| **Transport** | `total_transport_distance_km`| Total kilometers traversed by dispatched convoys |
| | `total_transit_hours` | Total hours vehicles spent in transit |
| | `average_delay_hours` | Mean transit delay caused by weather or degraded roads |
| | `maximum_delay_hours` | Peak transit delay experienced by any single convoy |
| **Fleet** | `vehicle_utilization_rate` | Fraction of fleet actively engaged in transit |
| | `active_fleet_count` | Total vehicles deployed |

## 8. Delta Calculations & Directionality (`MetricDelta`)

For every metric, the evaluator computes:
- $\text{absolute\_delta} = \text{optimized} - \text{baseline}$
- $\text{relative\_delta\_percent} = \frac{\text{absolute\_delta}}{|\text{baseline}|} \times 100\%$
- Qualitative direction: `IMPROVED`, `DEGRADED`, or `UNCHANGED`

### Directionality Rules
- **Lower is Better**: `unmet_demand`, `stockout_events`, `stockout_duration_hours`, `average_delay_hours`, `transport_distance_km`.
- **Higher is Better**: `fulfillment_rate_percent`, `time_to_zero_hours`.

A negative delta for transport distance is an improvement, but an increase in transport distance is categorized as `DEGRADED` (higher cost) while potentially contributing to a net operational improvement.

---

## 9. Status Classification Rules

PRAVAH avoids artificial monolithic score thresholds. Verdicts are classified via transparent multi-objective rules:

1. **`INVALID`**: State snapshot hash mismatch, source inventory depletion before dispatch, vehicle overload, or blocked route dispatch attempt.
2. **`IMPROVED`**: Service metrics (unmet demand, stockout events, fulfillment rate) improved with no increase in transport distance or costs.
3. **`MIXED`**: Service metrics improved significantly, but required an intentional tradeoff (e.g., increased transport distance or fleet deployment).
4. **`DEGRADED`**: Service metrics deteriorated compared to the baseline.
5. **`INCONCLUSIVE`**: No meaningful difference between baseline and optimized runs (deltas $< 0.1\%$).

## 10. Multi-Dimensional Tradeoff Analysis

The evaluator produces a structured operational tradeoff ledger:
```json
{
  "SERVICE": "IMPROVED",
  "RISK": "MITIGATED",
  "TRANSPORT_COST": "INCREASED",
  "DELAY": "REDUCED",
  "FLEET_UTILIZATION": "ACTIVE_CONVOYS_DISPATCHED"
}
```
This enables operational commanders to evaluate whether an 80% reduction in forward stockouts justifies deploying additional fuel convoys over high-altitude bypasses.

---

## 11. Critical-Node Trajectory Analysis

For every high-priority forward defense post (`FP-01` to `FP-06`) and regional hub (`RH-01` to `RH-03`), the evaluator tracks:
- `baseline_stockout`: Did stockout occur in the baseline?
- `optimized_stockout`: Did stockout occur under intervention?
- `survival_hours_difference`: Additional hours the forward post survived before depletion.
- `stockout_prevented`: Boolean indicator whether intervention entirely averted an otherwise certain stockout.

## 14. Optimizer Objective vs. Simulated Operational Outcome

A core conceptual principle enforced in Phase 3B:
> **The mathematical objective function is NOT the operational outcome.**

- The optimizer minimizes a synthetic weighted scalar objective:
  $$\min \sum c_{\text{trans}} x + \sum c_{\text{short}} s + \sum c_{\text{risk}} x + \dots$$
- The simulator evaluates real non-linear physics:
  - Exact hourly inventory step transitions ($I_{t+1} = I_t + \text{receipts} - \text{demand}$).
  - Actual route transit speeds influenced by dynamic blizzards and road blockages.
  - Vehicle turn-around delays and actual arrival hours.

Minimizing the mathematical cost does not guarantee success if parameters are miscalibrated. By logging both the mathematical objective and the physical simulated deltas, PRAVAH maintains auditable rigor.
